### What the code does now

- **The scraper already collects food details.** [MenuConstructor.ts](<C:/Users/maxsi/OneDrive/Documents/ChatGPT/CS320 Project/cs320-project/BackEnd/src/scraper/MenuConstructor.ts:27>) reads nutrition, ingredient, and allergen attributes while parsing each menu. It does not need to visit a separate page when someone clicks a food.
- **Scraping 14 days is mostly sequential within each location.** The four dining commons and category pages start in parallel, but each commons fetches its 14 days one at a time. Category pages also process their listed locations and dates sequentially ([diningHallParser.ts](<C:/Users/maxsi/OneDrive/Documents/ChatGPT/CS320 Project/cs320-project/BackEnd/src/scraper/parsers/diningHallParser.ts:44>), [locationListPageParser.ts](<C:/Users/maxsi/OneDrive/Documents/ChatGPT/CS320 Project/cs320-project/BackEnd/src/scraper/parsers/locationListPageParser.ts:18>)).
- **Saving is highly sequential.** For every food, [populateMenu.ts](<C:/Users/maxsi/OneDrive/Documents/ChatGPT/CS320 Project/cs320-project/BackEnd/src/db/populateMenu.ts:23>) waits for a food insert, ingredient writes, allergen writes, and meal writes before moving to the next food. Each ingredient and allergen can require two database calls. It also inserts a new `menu_items` row on each run, so repeated scrapes can accumulate duplicates.
- **Other locations appear to be skipped during database population.** The parser nests them under category nodes and uses a lowercase `menus` key, while `populateMenu` looks for a top-level `Menus` key. Based on this code, it will process the commons but skip those nested locations. Some locations are also marked as special menu types and need separate handling. This needs an integration test against representative scraped data.
- **Visitors wait for database round trips.** A menu request performs three sequential queries; clicking a food performs three more. The frontend does not retain results between selections.

I found no production scheduler invoking `populateMenu` in the repository; the visible invocation is a test script. That means we also need to establish how and when production data is refreshed before relying on a warm cache.

### Recommended design

**1. Refresh data in a background job, independently of visitors.** Scrape today first across all supported locations, then future dates in order. Use a small, configurable concurrency limit across upstream requests, with timeouts, retries, and per-location failure handling. Publish today’s successful results as they finish rather than waiting for all 14 days and every location.

**2. Batch and make database writes repeatable.** Flatten the parsed locations correctly, collect foods and relationships in memory, then bulk upsert them in bounded batches or through a database function. Use a verified stable source identifier where available; don’t assume a food name uniquely identifies a recipe. Replace each location/date’s snapshot atomically so a failed refresh cannot leave a half-updated menu. Track the successful refresh time.

**3. Serve a complete location/day snapshot.** Add an endpoint that returns all meal periods and their stations, plus a deduplicated collection of food details. Fetch the underlying records in bulk, not by calling the existing food endpoint for every item. Cache the prepared snapshot on the server and invalidate or refresh it after a successful scrape. The existing individual endpoints can remain for compatibility.

**4. Preload in the browser.** Render the homepage immediately, then request today’s snapshots for all supported locations with bounded concurrency. Cache completed results and in-flight requests across navigation. Selecting a location or date promotes its request to the front; clicking a food uses the details already in its snapshot. Once today is ready, load nearby available dates in proximity order, subject to a measured bandwidth limit.

This removes the food-click request and makes the menu available as soon as its location’s preload finishes. It also separates **visitor speed** from **scrape speed**: batching the read path improves clicks immediately, while fixing the scraper and write pipeline keeps that fast data complete and fresh.

I’d implement the flattened location ingestion and complete-snapshot endpoint first, then the client preload. Before and after, measure scrape duration, database request count, snapshot size, and time from selecting a location to seeing its menu and food details. I haven’t benchmarked the live system, so the relative speedup still needs measurement.
